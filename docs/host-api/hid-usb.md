## 2. `device.*` I/O API (HID/rawusb/hybrid)

Return/padding conventions (docs writes-and-reads + corpus): `write`/`send_report` take `(byte[] data, int length)`; data shorter than `length` is **zero-padded**; **first byte is the Report ID**; for endpoints without report IDs the plugin prepends `0x00` and uses length+1 (QMK: 32-byte raw HID report sent as `[0x00, cmd, ...]` length **33** for stream data, length 32 for commands). Writes return `-1` on failure (181 call sites test `device.write(...) === -1`, e.g. `ADDON\...\GMMK_Pro_QMK_Keyboard.js:249`); otherwise bytes written (UNKNOWN exact). Reads return `int[]` **including the report-ID byte at index 0** (QMK parses `data[1]` as command; `BUND\Hyte\Hyte_Keeb_TKL_Keyboard.js:96` `packet[0] === WHEEL_REPORT_ID`); on timeout empty array and `getLastReadSize()===0`.

`Type()==="hybrid"` ⇒ engine opens **both** the HID path (hidapi; `write/read/send_report/get_report` on the `Validate`d endpoint) **and** a libusb handle on the same device (WinUSB/libusbK) so `bulk_transfer`/`control_transfer` work. Patterns:
- **Alienware Gen3 monitors** (`BUND\Alienware\Alienware_Monitor_Gen3_Controller.js`, VID 0x187c PIDs 0x100E/0x1010, `Validate: interface===0`): endpoint chosen at runtime via `getHidEndpoints()` ↔ library `{interface:0, usage:0x00DA, usage_page:0xFFDA, collection:0}` then `set_endpoint(4-arg)`. Per LED: `write([0x00,0x40,0xE1,0x01],192)` (pre-fetch token) → `control_transfer(0xA1,0x01,0x0100,0,[],192,1000)` (GET_REPORT Input, 16-byte token) → key derivation (OEM key XOR scheme, lines 192-257) → `write(login_packet,192)` (`[1]=0x40,[2]=0xE1,[3]=0x02,[65..72]=key`) → `write(RGBData,192)` (`[1]=0x40,[2]=0xC6,[7]=0x0A,[9]=0x6E,[11]=0x82,[65..68]=51 87 D0 04,[69]=led,[70..72]=RGB,[73]=0x64,[74]=CRC xor`) → `pause(delayRGB=200)`.
- **Asus Ryujin I/II/III** (`BUND\Asus\ASUS_Ryujin_AIO_Controller.js`, 0x0B05 PIDs 0x18AE/0x1988/0x1AA2, `Validate: iface 0||1`): HID endpoint `{iface 0|1, usage 0xA1, usage_page 0xFF72}`; commands via `write([0xEC, cmd...],65)` + `read([replyId],65)` (fan/pump telemetry 0x99/0x9A/0xA0/0xA1, RGB `0xEC 0x40 0x80 00 05 + RGB`); Ryujin III LCD: handshake `EC D0 / EC 51 20 / EC 7F 03 00 84 03` then per frame 230400 bytes BGR888 via `bulk_transfer(0x01, chunk4096, size, 500)` and commit `write([0xEC,0x7F,0x03,0x00,0x84,0x03,0,0],65)`.
- **Lian Li Uni Fan SL V2 / AL V2 / AL 1.1** (`BUND\Lian Li\Lian_Li_Uni_Fans_SL_V2.js` 0x0CF2 `[0xA103,0xA105]`, AL_V2, AL_1.1 0xA101; `Validate: interface===1`): RGB via `write([0xE0, 0x30+ch]+RGB, 353)` + commit `send_report([0xE0,0x10+ch,0x01,0x02],353)`; setup via `send_report/get_report(...,32)` pairs; fan RPM via vendor control `control_transfer(0xC0,0x81,0,0xD800+2*ch,[],65,1000)` and AL 1.1 writes `control_transfer(0x40,0x80,...)`. (SL 1.2 `[0xA100,0xA106]` is pure `rawusb` with the same packets.)
- **NZXT Kraken Elite/Z3** switch at runtime: `device.setProtocol("hybrid")` when LCD enabled (bulk `0x02` with 20-byte header `12 FA 01 E8 AB CD EF 98 76 54 32 10 ...` + frame), `setProtocol("hid")` otherwise.
- rawusb-only examples: Aqua Computer D5/Farbwerk (`bulk_transfer(0x02, 364-byte, 364)`), Lian Li Universal Screen 8.8 (DES-CBC encrypted 512-byte header + JPEG, `bulk 0x01/0x81`), Thermalright LCD (`bulk 0x01/0x81`, 64), Turzx Screen 8.8.

## 5. Multi-PID plugins, matching and endpoint selection
- 137 files use `ProductId(){return [..]}`, ≈120 use `Object.keys(lib.PIDLibrary)` (strings). The loader registers **one `VID:PID` key per element** (log: 656 modules → 1366 USB plugins). Collisions are resolved by overwrite order; two real collisions on this machine: `0x320F:0x5088` (QMK GMMK Numpad vs EVision controller) and `0x3434:0x0DA0` (two Keychron K10 V2 files).
- Matching algorithm (inferred from logs/plugins): enumerate USB parents (`USB\VID_xxxx&PID_xxxx\serial`), group all HID collections under the parent, look up plugin by `VID:PID`, filter collections with `Validate(endpoint)` (fields `interface` = `MI_xx` (0 for a non-composite USB device, -1 only without a USB interface), `usage`, `usage_page`, `collection` = the Windows `ColNN` number, 0 for a single-TLC interface; see §Endpoint tuple semantics), open them; the first validated one is active until `set_endpoint`. Plugins then call `device.productId()` to pick a per-PID config (`PIDLibrary[device.productId()]`, numeric key lookup on an object keyed by hex literal ⇒ engine must return a Number).
- Inside Validate some plugins consult `device.productId()` ⇒ `device` global must be bound before Validate runs.
- Plugins read `device.getHidEndpoints()` to select among several interface/usage combos, and `device.getHidInfo()` for report sizes of the active endpoint.
- Helper modules (`*_Protocol.js`, `*.test.js`, `*.bak.js`) in plugin dirs are evaluated and rejected by the ProductId check (harmless warnings); an open-source loader should skip modules without `VendorId`+`ProductId` silently.

## 6. Keyboard layout conventions and QMK raw HID protocol
- Convention (all 185 QMK plugins, most keyboards): three parallel arrays `vKeys` (hardware LED index per logical key, used as `rgbdata[vKeys[i]*3]`), `vKeyNames` (canonical key names from key-names doc: `"Esc","F1".."F24","Print Screen","Scroll Lock","Pause Break","`","1".."0","-","=","Backspace"/"Back Space","Tab","Q".."P","[","]","\\","Caps Lock","A".."L",";","'","Enter","Left Shift","Z".."M",",",".","/","Right Shift","Left Ctrl","Left Win","Left Alt","Space","Right Alt","Right Win","Menu","Fn","Right Ctrl","Insert","Home","Page Up","Del","End","Page Down","Up Arrow","Left Arrow","Down Arrow","Right Arrow","NumLock","Num /","Num *","Num -","Num 7".."Num 0","Num +","Num Enter","Num .","ISO_#","ISO_<","ABNT2_/","AudioMute","AudioVolume Up/Down","MediaNextTrack","MediaPlayPause","MediaPreviousTrack","MediaStop"`), `vKeyPositions` (`[x,y]` grid cells). ANSI/ISO variants swapped at runtime via `device.setControllableLeds(names, positions)` after reading the unique identifier.
- QMK plugins: `Validate(endpoint){return endpoint.interface === 1;}` (185/185 — the QMK raw-HID interface, usage_page 0xFF60 usage 0x61), no `Type()` (HID), `Documentation() "qmk/..."`, `DefaultScale 8.0`.
- Protocol (`PluginProtocolVersion "1.0.6"` 183 files, `"1.0.5"` 1): host → keyboard **32-byte raw HID report** written as `device.write([0x00, cmd, ...], 32)` (report id 0 prepended): `0x21` GET_QMK_VERSION → reply `[0x00,0x21,major,minor,patch]`; `0x22` GET_PROTOCOL_VERSION → `[.,0x22,M,m,p]`; `0x23` GET_UNIQUE_IDENTIFIER → `[.,0x23,b1,b2,b3]` (b3==6 ⇒ ISO in GMMK Pro); `0x24` STREAM_RGB_DATA: `device.write([0x00,0x24,startLedIdx,ledCount, r,g,b ×≤9], 33)` (9 LEDs/packet; keyboard may reply 0x24 ⇒ host re-sends); `0x25` SET_SIGNALRGB_MODE_ENABLE; `0x26` SET_SIGNALRGB_MODE_DISABLE (hardware mode); `0x27` GET_TOTAL_LEDS → `[.,0x27,count]`; `0x28` GET_FIRMWARE_TYPE → `[.,0x28, 1=mainline QMK | 2=VIA]`. Reply reading: `device.read([0x00], 32, 10)` in a drain loop until `getLastReadSize()===0`; VIA firmware sends a duplicate packet that is discarded. Shutdown: `SystemSuspending` ⇒ stream black; else `shutdownMode==="SignalRGB"` ⇒ stream `shutdownColor`, else `0x26`. Names of command constants are the SRGBmods `signalrgb.c` names (inferred; verify against `github.com/SRGBmods/QMK-Binaries/GPL`).

## 8. Lightloom extensions for generic HID drivers

Not part of the SignalRGB surface; plugins that use them run only in Lightloom. They let one
plugin drive a standard HID collection on any device (the first user is
`plugins/hid-lamparray/`, HID LampArray).

- **`HidUsages()` export** -> `[[usagePage, usage], ...]`, for example `[[0x59, 0x01]]`. Read
  with the other metadata exports (call-if-function). A plugin that exports it needs no
  `VendorId`/`ProductId`. The host offers it for a device when no plugin claims the device's
  VID:PID and one of the device's top-level collections has one of these usages; a VID:PID plugin
  always wins. Manifests declare it as a `hidUsage` claim (`schemas/plugin-manifest-v2`).
- **`device.getHidReportFields()`** -> the open collection's report descriptor, parsed by the
  host (`lightloom-hid-desc`; on Windows the descriptor hidapi reconstructs from the collection's
  preparsed data), or `null` when the backend cannot read it. No report I/O.
  ```js
  {
    usagePage: 0x59, usage: 0x01,
    reports: [{ kind: "feature", reportId: 1, bytes: 23 }, ...],   // bytes include the report id
    fields: [{
      kind: "feature", reportId: 1,
      bitOffset: 16, bitSize: 32, count: 5,      // bits after the report-id byte, little-endian
      flags: 3,                                  // main-item flags: bit 0 constant, bit 1 variable
      logicalMin: 0, logicalMax: 2147483647,
      collection: [0x59, 0x02],                  // innermost collection around the field
      usages: [[0x59, 0x04, 0x04], [0x59, 0x05, 0x05], ...],   // [page, min, max] in order
    }, ...],
  }
  ```
  Element `i` of a variable field takes the `i`-th declared usage and the last one when there
  are fewer usages than elements (HID 1.11, 6.2.2.8). Unnumbered collections report
  `reportId: 0`, and their report arrays still start with that `0x00` byte, like every other
  host call.


## Engine requirements (summary)

- ES-module JS runtime per device with host globals `device`, `console`, and import resolver for `@SignalRGB/{serial,udp,tcp,dtls,base64,lcd,Errors(.js),DeviceDiscovery,permissions,systeminfo,performance,appInfo}` plus relative `./x.js` imports; no DOM globals.
- Plugin crawler: evaluate every .js, require exports Name/VendorId/ProductId (int | int[] | numeric-string[] via Object.keys), register one entry per VID:PID, log and overwrite on collision, skip helper modules gracefully.
- USB enumeration on Windows: SetupAPI/WMI parent devices (USB\VID_&PID_\serial), group HID collections (hidapi paths with MI_xx and collection index), expose {interface, usage, usage_page, collection} to Validate(endpoint) and getHidEndpoints(); interface = bInterfaceNumber (0 when the path has no `&MI_xx` but the device is USB), -1 only for non-USB transports (Bluetooth/BLE HID); collection = `ColNN` parsed as two hex digits (1-based), 0 when the interface has a single top-level collection.
- HID I/O on the active endpoint: write (output report, report-id byte first, zero-pad to length, return -1 on error), send_report/get_report (feature), read(reportId[], len, timeout=100ms; non-blocking when 0) returning report-id-prefixed int[] and tracking getLastReadSize(), input_report (GET_REPORT Input), clearReadBuffer(), flush(), getHidInfo() {readLength, writeLength}, set_endpoint(3/4-arg), productId(), getDeviceInfo() {product}.

- Serial backend for Type 'serial': bind COM port belonging to the matched USB VID:PID, serial.connect({portName?, baudRate, dataBits, stopBits, parity}), disconnect, isConnected, write, read(max, timeout), readAll, availablePorts, getDeviceInfo, getPortName, getBaudRate.
- Per-device engine thread calling Initialize() once, Render() at setFrameRateTarget fps (default needed), on<Prop>Changed()/onBrightnessChanged() before Render, Shutdown(systemSuspending) on exit/remove/sleep; device.pause(ms) sleeping that thread.
- Canvas sampling: device.color(x,y) from the 320x200 canvas via Size/DefaultPosition/DefaultScale + LedPositions, brightness applied; setSize/setControllableLeds at runtime; subdevice and channel APIs (addChannel/channel().getColors/LedCount/shouldPulseColors, createColorArray with color-order strings, SetLedLimit, createSubdevice*, SetIsSubdeviceController).
- Settings system: ControllableParameters/addProperty/removeProperty/getProperty objects (types color, combobox, boolean, number, textfield, hue, keycode; min/max/step/default/values/live/order/filter) exposed as module globals, persisted per device.
- Feature globals via device.addFeature: battery (setBatteryLevel/State, constants, lowBatteryWarningLevel), keyboard (sendHid VK injection, sendKey by name, sendEvent to macro system), mouse (sendHid/sendEvent), udp, dtls (PSK), base64.

- Power events: on system suspend stop render threads and call Shutdown(true); on resume re-Initialize; on app shutdown call Shutdown(false).
- QMK raw HID support needs nothing special beyond the HID layer (interface 1, 32-byte reports, report id 0 prepended, 10 ms read timeouts, drain loops).

## Endpoint tuple semantics (verified in M0 spike C, 2026-10-18)

Measured on the reference machine with `lightloom devices` (read-only enumeration) and checked
against the plugin corpus, hidapi 2.6.7 and SignalRGB's logs. This supersedes the earlier
assumptions above (interface -1 for MI-less paths, 0-based collection index).

- **interface** = USB `bInterfaceNumber` (the `&MI_xx` suffix). A non-composite USB device has
  no `&MI_xx` in its HID path and reports **0** (hidapi does the same). **-1** is reserved for
  HID devices without a USB interface (Bluetooth/BLE). Every corpus `Validate` that accepts -1
  also accepts 0, so no plugin depends on -1 alone.
- **collection** = the Windows top-level-collection number from the `&ColNN` suffix. Windows
  writes it as **two uppercase hex digits** (hidclass.sys format
  `HID\VID_%04X&PID_%04X&Col%02X&UP:%04X_U:%04X`; Microsoft "HIDClass Hardware IDs for
  Top-Level Collections"), 1-based. An interface with a single top-level collection has no
  `&ColNN` and reports **0**.
  - Evidence: a Sonix-family keyboard plugin hard-codes `{interface 1, usage 0x0092,
    usage_page 0xFF1C, collection 4}`; the Sonix 320F:5064 here exposes exactly
    `0xFF1C/0x0092` at `MI_01&Col04`. Razer `set_endpoint(1, 0, 1, 5)` matches `MI_01&Col05`.
    Across the corpus, 46 distinct literal tuples use collection values 0..6, none
    contradictory.
- **Grouping**: HID interfaces are grouped under their USB parent device
  (`USB\VID_xxxx&PID_xxxx\<serial>`), found by walking the PnP tree with cfgmgr32. The parent
  is accepted only when its VID/PID equals the endpoint's, so Bluetooth HID devices are never
  merged under the Bluetooth radio's USB node; they fall back to serial or instance-prefix
  grouping. The device key is `vid:pid:<serial>`, where the serial comes from the parent's
  instance id (generated ids such as `6&XXXXXXXX&0&10` become `6-XXXXXXXX-0-10`, the form
  SignalRGB logs).
- **Linux (M7)**: hidraw tuples must follow the same rules: collection 0 for a single-TLC
  interface, otherwise the 1-based TLC index in report-descriptor order (`lightloom-hid-desc`);
  interface 0 for non-composite USB, -1 for Bluetooth.
