# Lenovo Legion per-key lighting over USB (`048D`, usage `FF89:07`)

Plugin: `plugins/lenovo-legion-usb/`. It has not been tested on hardware (`tested` is empty).

It drives the per-key keyboard lighting of Lenovo Legion laptops, plus their logo, vent and
"neon" strips where the laptop has them. They all sit behind the laptop's ITE USB lighting
controller. OpenRGB has two protocols for these laptops, and this plugin carries both:

- **legacy**: Legion Y740, Legion 7 / 7S Gen 5 and Gen 6. In OpenRGB this is `LenovoUSBController`.
- **gen7**: Legion 7 / 7S Gen 7, Gen 8 and Gen 9, and Legion 7 Gen 10. In OpenRGB this is
  `LenovoGen7And8USBController`, and the plugin uses its Direct mode only.

**Held back:** `C195`, the Lenovo Legion 5 Gen 10 (24-zone keyboard). OpenRGB gives it no Direct
mode (`IsKeyboardOnlyDevice`). It is driven only through modes that OpenRGB writes into the
laptop's lighting profiles with `SAVE_PROFILE` (`0xCB`), and HueDeck does not write
profiles.

`Validate` accepts usage page `0xFF89`, usage `0x07`, on any interface.

### Layout selection (legacy)

The `RGBController_LenovoUSB` constructor sends information requests. It then reads byte 4 of each
reply; if there is no reply, or a reply of 4 bytes or fewer, it uses the default.

| PID | Request | Rule |
|---|---|---|
| `C935` | `0x01`, then `0x04` | 0x01: ≤ 100 → 15", else 17" (also with no reply). 0x04: 16..48 → ISO, else ANSI |
| `C956` | `0x04` | 41 → JIS; 16..40 → ISO; else ANSI |
| `C957` | `0x01` | `0x97` → JIS; `0x91` → ISO; else ANSI |
| `C968` | `0x07` | 41 → JIS; 16..40 → ISO; else ANSI |
| `C967` | `0x01` | `0x97` → JIS; `0x8F` → ISO; else ANSI |

## Grid

LED order and the bytes on the wire are OpenRGB's: zones in order, then each zone's LEDs from
start to end. Placement is HueDeck's own:
- A matrix zone (the keyboard) uses its OpenRGB map cells.
- Each linear zone is one row below it.
- Consecutive one-LED zones share one row.

In OpenRGB's Y740 17" ISO map, the `Key: #` LED (number `0x2B`, index 68) has no cell. HueDeck
puts it in the next free cell to the right of the key before it.

The Legion 7 Gen 6's 99-LED neon strip makes that grid 99 cells wide.

## Protocol: legacy (Y740 .. Y760S)

All reports are 192-byte feature reports with report id `0x07`.

- **Initialize.** First `07 B2` (`setDeviceSoftwareMode`): "required for the device [to] listen to
  the software protocol". Then the information requests from the table above. Each request is
  `07 <id>`, followed by a GET_FEATURE of report `0x07`. These are read-only queries; OpenRGB's
  trace-level dump also queries ids 1..7.
- **Frame** (`DeviceUpdateLEDs`). Runs of LEDs with the same zone id (`value >> 8`) go to
  `setZoneLeds`. That sends `07 <A0 + zone> <count> 00`, then `<led number> R G B` for each LED,
  at most 47 (`0x2F`) LEDs per report. On the Y740 and Y750, the single-LED extra zones carry
  zone id 1, like the keyboard. So they are sent in the keyboard's run, to zone `A1`. HueDeck
  skips a frame whose colours did not change and resends it after 1 s.
- **Shutdown.** `07 B1` (`setDeviceHardwareMode`). OpenRGB sends it when the controller is
  destroyed: it "releases the device from software mode so that onboard controls can be used".

## Protocol: gen7 (Gen 7 .. Gen 10)

All reports are 960-byte feature reports with report id `0x07`. The header is `07 <cmd> C0 03`,
except on the Gen 10 (`C197`), where bytes 2-3 hold the payload length (little endian).

- **Initialize.** `getCurrentProfileId`: `07 CA C0 03` (Gen 10: `07 CA 01 00`), then a
  GET_FEATURE of report `0x07`. The profile is byte 4 of the reply, or 1 if there is no reply.
  Then, except on the Gen 10, `setLedsDirectOn`: `07 D0 C0 03 01 <profile>`.
- **Frame** (`setLedsDirect`). `07 A1 C0 03`, then `<led lo> <led hi> R G B` for every LED, where
  the value is `zone id << 8 | led number`. On the Gen 10, the report is `07 A1 <len lo> <len hi>`
  with length = 5 × the LED count, and it follows a `07 D0 02 00 01 <profile>` on every update.
  OpenRGB's comment: "Gen10 may ignore A1 updates unless D0 is reasserted". HueDeck skips a frame
  whose colours did not change and resends it after 1 s.
- **Shutdown.** `setLedsDirectOff`: `07 D0 C0 03 02 <profile>` (Gen 10: `07 D0 02 00 02
  <profile>`). OpenRGB sends this when it leaves Direct. The laptop then shows its active
  profile's own lighting again.

### Left out of gen7, and why

- `SAVE_PROFILE` (`0xCB`, `setLedsByGroup`). When OpenRGB's user switches to Direct from another
  mode, OpenRGB also writes a Direct "group" into the active lighting profile. That is a write to
  the laptop's stored profiles, so HueDeck never sends it. OpenRGB itself enables Direct with
  `D0 01` alone on other paths: when the mode is already Direct, and on every Gen 10 update. If
  Direct does not take on a Gen 7..9 without that profile write, this is the reason. Check this
  on hardware.
- `GET_BRIGHTNESS` (`0xCD`) and `GET_PROFILE` (`0xCC`). These are read-only queries in OpenRGB's
  constructor. They only fill OpenRGB's mode list, so HueDeck does not send them.
- `SET_BRIGHTNESS` (`0xCE`), `SWITCH_PROFILE` (`0xC8`), and every hardware effect: these are
  never sent.

## Safety

- Commands sent: legacy `B2`, `B1`, information requests `01`/`04`/`07`, and zone reports
  `A1`..`A4`. Gen7: `CA`, `D0`, `A1`. A test checks that nothing else is sent.
- No profile, brightness or other setting is ever written.

## Untested

Every product id. These questions need the hardware:
- whether Gen 7..9 enter Direct with `D0 01` alone (see above);
- whether the layout queries answer as OpenRGB expects;
- whether the Y740 15" grid matches the keyboard.
