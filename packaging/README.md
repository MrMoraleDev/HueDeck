# packaging/

Distribution artifacts for Lightloom. Release builds are produced by
`.github/workflows/release.yml` (cargo-dist planned; cargo-auditable + CycloneDX SBOM
today). Nothing here is signed yet; Authenticode via SignPath OSS is the planned step
for Windows (see the SIGNING block in the release workflow).

`wix/` (Windows MSI), `winget/` (manifest templates), `msix-identity/`, `systemd/`, `udev/`, `sysusers.d/`,
`modules-load.d/`, `appimage/`, `flatpak/`, `flathub/` and `nfpm/` are real. `wix/lightloom.ico` is the app icon (rendered from
`docs/brand/lightloom-icon.svg`), also embedded in every Windows executable by `crates/lightloom-winres`.

## Windows (MSI, winget)

### What gets built

- `tools/package/stage-windows.ps1` stages one directory: `lightloomd.exe`, `lightloomw.exe`
  (starts the daemon without a window, and the tray icon), `lightloom-tray.exe` (the
  notification-area icon), `lightloom.exe`, `lightloom-renderer.exe` and its CEF
  runtime, `lightloom-setup.exe` and `lightloom-iobroker.exe` (RAM lighting), `pawnio-modules/`
  (PawnIO.Modules 0.2.11: `SmbusPIIX4.bin`, `SmbusI801.bin`, `Echo.bin`, `COPYING` and their sources, every
  file SHA-256 pinned, fetched by `tools/package/fetch-pawnio-modules.ps1`), `ui/`,
  `plugins/`, `effects/`, the licence texts, `privacy.md` and
  `THIRD-PARTY/CEF-Chromium-CREDITS.html`. About 400 MB, most of it Chromium.
- The **portable zip** is that directory: unzip anywhere and run `lightloomw.exe --open`
  (or `lightloomd.exe --open` to see the log in a console).
- The **MSI** (`packaging/wix/build.ps1 -Stage <dir>`, WiX Toolset 5.0.2 as a .NET tool)
  packs the same directory. `release.yml` builds both for a tag; `ci.yml` checks that the
  WiX sources build on a stand-in stage.

### Installer design

The user's decisions: it works out of the box; Lightloom itself installs per user without
administrator rights; RAM lighting (the PawnIO driver) is the user's choice, offered and
checked by default.

- **Per-user MSI** (`Scope="perUser"`), installed to `%LOCALAPPDATA%\Programs\Lightloom`; no
  UAC prompt for the install itself. Settings stay in `%LOCALAPPDATA%\Lightloom` and
  `%APPDATA%\Lightloom` (shared with the portable build).
- **Options page**: *RAM and motherboard lighting (installs the PawnIO driver)*, with a short
  explanation, checked by default; *Start Lightloom when I sign in* (an `HKCU\...\Run` value
  starting `lightloomw.exe`, which runs the daemon with a hidden console and logs to
  `%LOCALAPPDATA%\Lightloom\logs`, like the portable `start-lightloom.ps1` did), checked by
  default. The sign-in entry belongs to the user, not to an MSI component: `lightloomw.exe
  --autostart on` writes it after a first install with the option checked, the tray's
  *Start at sign-in* turns it on and off, an upgrade keeps it as it was (rewriting it only if
  it was there before), a repair never brings it back, and uninstall removes it
  (`lightloomw.exe --autostart off`).
- **Tray icon**: `lightloomw` starts `lightloom-tray.exe` (one per session) when it sits next to
  it; `--no-tray` skips it. `lightloomw.exe --stop` closes it as well, so upgrades and uninstalls find no file in use. Menu: Open dashboard, Pause/Resume lighting, Brightness presets,
  Start at sign-in, Quit Lightloom (`POST /v1/shutdown`, plugins restore their devices). A Start-menu shortcut *Lightloom* (`lightloomw.exe --open`: starts the daemon if needed
  and opens the dashboard) is always created. The Finish page offers *Start Lightloom now*.
  English and Italian strings (`-Culture it-IT`).
- **RAM lighting** is the only privileged part. When the option is checked, pressing Finish
  starts `lightloom-setup.exe --pawnio-install --smbus --elevate --pause`, which asks Windows
  for permission once (UAC) and, in its own window: reads PawnIO's version from its uninstall
  entry and, when it is missing or older than 2.2.0, downloads the official
  `PawnIO_setup.exe` 2.2.0 from `github.com/namazso/PawnIO.Setup` into
  `%ProgramFiles%\Lightloom\downloads` (administrators-only), checks its size, SHA-256
  (`1f519a22…3032`, pinned in `lightloom-iobroker/src/pins.rs`) and Authenticode signer
  (`namazso.eu`), runs it with `-install -silent` and deletes it; then copies the bundled
  pinned modules and the broker to `%ProgramFiles%\Lightloom` and registers the
  `LightloomIoBroker` service. A declined prompt, no network or a failed check changes nothing:
  the install itself has already succeeded, RAM lighting stays off, and the dashboard offers
  it again (Settings → PawnIO / RAM lighting → Install). A running daemon notices the service
  when it starts and opens its buses.
- **Why not a per-machine MSI or a Burn bundle?** A per-machine MSI would need administrator
  rights for Lightloom itself, which the user did not want. A WiX Burn bundle that chains a
  per-user MSI with a per-machine package registers itself per machine and asks for
  elevation for the whole chain, and its option checkbox would need a custom bootstrapper
  theme. Running the one elevated step from the per-user MSI through the same helper the
  dashboard uses keeps a single code path (Rust, tested) for both, and the elevation visible
  and separate.
- **Silent installs** (`msiexec /qn`, winget) install Lightloom only: they never raise a UAC
  prompt. RAM lighting is then one click in Settings.
- **Upgrades** (major upgrade, same `UpgradeCode`) first ask a running daemon to stop
  (`lightloomw.exe --stop`: `POST /v1/shutdown`, so plugins restore their devices). With the
  option checked, Finish runs the helper again, which updates the broker (stop, replace,
  register) and keeps PawnIO when it is current.
- **In-app updates** (Settings → Updates, `crates/lightloom-daemon/src/update.rs`) rely on
  exactly this: the daemon downloads `Lightloom-<x.y.z>-x64.msi`, checks it against the
  release's `SHA256SUMS` (written over every release file by the `assemble` job of
  `release-build.yml`, which also fails when the MSI is not named that way) and starts
  `msiexec /i` detached from itself. The package's
  `StopLightloom` action then stops the daemon and the tray before `InstallValidate`, so no file
  is in use, and Finish starts the new version. Cancelling the wizard leaves the running version
  alone. Keep the MSI name, the per-user scope and `StopLightloom` as they are, or update the
  updater with them.
- **Uninstall** stops the daemon, then, when the `LightloomIoBroker` service exists, runs
  `lightloom-setup.exe --smbus --uninstall --elevate` (one UAC prompt) to remove the service and
  its files under `%ProgramFiles%\Lightloom`. **PawnIO stays installed**, because other programs
  (fan and monitoring tools) use it; the dashboard and `docs/privacy.md` say so. If that prompt
  is declined, `sc.exe delete LightloomIoBroker` from an elevated prompt removes the service.
- **Validation**: ICE38/ICE64/ICE91 are suppressed (`build.ps1`): they assume per-machine
  locations and flag every harvested file under the user profile.
- **Signing**: not yet; SignPath (OSS) signs the executables and the MSI in `release.yml`
  once enabled. Until then Windows SmartScreen and the UAC prompt show an unknown publisher.

### Privacy

The PawnIO download is the only network access Lightloom makes on its own; see
[`docs/privacy.md`](../docs/privacy.md).

### winget

`winget/render.ps1 -Tag vX.Y.Z` downloads the release's `SHA256SUMS` and MSI, checks the MSI
against it, and fills the templates (version and `ProductCode` read from the MSI, SHA-256, URL)
into `winget/manifests/l/Lightloom/Lightloom/<version>/` (git-ignored). The manifests declare
`InstallerType: wix` and `Scope: user`; WiX generates a new ProductCode for every build (fixed
`UpgradeCode`, major upgrades), which is why it is read from the published MSI. Validation and
submission (`wingetcreate submit` or a pull request to `microsoft/winget-pkgs`):
`winget/README.md`.

## Linux (systemd user unit, udev)

User-facing install guide and porting notes: `docs/linux-porting.md`. The Linux tarball is
staged by `tools/package/stage-linux.sh` (the counterpart of `stage-windows.ps1`).

- `systemd/lightloomd.service` is a `systemd --user` unit: copy to
  `~/.config/systemd/user/`, then `systemctl --user enable --now lightloomd`. It expects the
  daemon at `~/.local/bin/lightloomd`, a symlink into the unpacked tarball (the AppImage and
  the Flatpak print the unit with their own command: `--systemd-unit`).
- `udev/70-lightloom.rules` is generated from the first-party plugin manifests by
  `lightloom udev generate --plugins plugins --out packaging/udev/70-lightloom.rules`; a
  `lightloom-cli` test fails when it is stale. It tags only the `hidraw` (or `usb_device`,
  `tty`) node of each claimed VID:PID with `uaccess` (an ACL for the logged-in seat user)
  and puts the `/dev/i2c-*` adapters Lightloom uses (by adapter name) in group `i2c` for
  SMBus plugins. Install steps:
  `udev/README.md`. With imported plugins, generate your own file the same way.
- `sysusers.d/lightloom.conf` creates the `i2c` group (`systemd-sysusers`).
- `modules-load.d/lightloom.conf` loads `i2c-dev` at boot (the `/dev/i2c-*` nodes).

## Debian and RPM packages

`nfpm/build-packages.sh --stage <staged tree> --version <v>` builds
`lightloom_<version>_amd64.deb` and `lightloom-<version>-1.x86_64.rpm` with nFPM 2.47.0
(downloaded, SHA-256 checked) from the same staged tree as the tarball. The `linux` job of
`release-build.yml` runs it for every release.

- **Layout**: the staged tree in `/usr/lib/lightloom/` (with `lightloom-launch`, the
  AppImage's `AppRun`, for the menu entry), symlinks `/usr/bin/lightloomd` and
  `/usr/bin/lightloom`, the user unit `/usr/lib/systemd/user/lightloomd.service`
  (`ExecStart=/usr/bin/lightloomd`), `/usr/lib/udev/rules.d/70-lightloom.rules`,
  `/usr/lib/sysusers.d/lightloom.conf`, `/usr/lib/modules-load.d/lightloom.conf`, the desktop
  entry, icons (SVG and 512 px PNG) and metainfo under the Flathub id
  `io.github.MrMoraleDev.Lightloom`, docs in `/usr/share/doc/lightloom` (with the DEP-5
  `copyright` in the `.deb`), licences in `/usr/share/licenses/lightloom` (`.rpm`). File modes
  are set from a fixed list: 0755 for the four programs, 0644 for everything else.
- **Dependencies**: Chromium's runtime libraries (the list `ci.yml` installs for the
  renderer) and libpipewire, with glibc 2.39 or newer. The `.deb` uses Ubuntu 24.04 / Debian 13
  names (`t64`: `libasound2t64`, `libcups2t64`, `libatk1.0-0t64`, `libatk-bridge2.0-0t64`,
  `libatspi2.0-0t64`, `libpipewire-0.3-0t64`), the `.rpm` Fedora 40+ names. Recommends:
  `fonts-liberation` / `liberation-fonts`, `xdg-utils`.
- **Maintainer scripts** (`postinstall.sh`, `postremove.sh`, the same for both formats):
  `systemd-sysusers` for the `i2c` group, `modprobe i2c-dev`, `udevadm control --reload` and
  `udevadm trigger` for hidraw, USB, tty and i2c-dev devices; each step skipped where the tool
  or a running udev is missing. **The user service is never enabled or started**: each user
  runs `systemctl --user enable --now lightloomd`. Removal reloads udev and leaves the group.
- **Checks** in the workflow: `dpkg-deb --info/--contents` (and the expected paths),
  `lintian --fail-on error`, `rpm -qip`, `rpmlint` (errors fail; `nfpm/lintian-suppress` and
  `nfpm/rpmlintrc` skip a few tags that only concern the prebuilt CEF runtime, such as its
  embedded zlib/libpng copies and the renderer's `$ORIGIN` RUNPATH), then `apt install` of the
  `.deb` on the runner, `lightloomd --version` through `/usr/bin`, the unit
  (`systemd-analyze --user verify`), the group, the desktop entry, the metainfo, and removal.
- **Not yet**: package signing (the release's `SHA256SUMS` covers them), an apt/dnf repository,
  `chrome-sandbox` (the Chromium sandbox is off in every build).

## AppImage / Flatpak / Flathub

- `appimage/`: built with linuxdeploy by the `linux` job of `release-build.yml`; the staged
  tree, CEF effect renderer and runtime included, sits in `usr/lib/lightloom`. AppImages
  cannot install udev rules: `--setup-help` prints the commands. See `appimage/README.md`.
- `flatpak/`: `org.freedesktop.Platform` 25.08; device access through `--device=all` plus
  the host-installed udev rules above (a Flatpak cannot install them), `--share=network`
  for the 127.0.0.1 dashboard. No CEF renderer yet. Built and linted with Flathub's linter
  weekly by `.github/workflows/flatpak.yml`. See `flatpak/README.md`.
- `flathub/`: app id `io.github.MrMoraleDev.Lightloom`. `prepare.sh --tag vX.Y.Z` writes the
  files for the Flathub repository (manifest with a git source pinned to the tag and commit,
  the cargo/npm source lists generated from that commit's lock files, `flathub.json`).
  Submission steps, and why the missing renderer does not block it: `flathub/README.md`.

## Release workflows

- `.github/workflows/release-build.yml` (reusable) builds everything a release ships: the
  Windows zip and MSI, the Linux tarball (`.tar.xz`), AppImage, `.deb` and `.rpm`, CycloneDX SBOMs for both
  targets, all with cargo-auditable; checks that two Linux builds are bit-identical; writes
  `SHA256SUMS`; uploads the `lightloom-release` artifact. It publishes nothing.
- `.github/workflows/release.yml` calls it on a `v*` tag and makes a draft release from the
  artifact. The tag must match `[workspace.package] version` in Cargo.toml.
- `ci.yml`'s `release-dry-run` calls it weekly and on manual dispatch, so the release steps
  run before any tag does. Details: `docs/linux-porting.md`, "Release".
