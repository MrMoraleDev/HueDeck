# packaging/flathub

Everything needed to put Lightloom on Flathub as `io.github.MrMoraleDev.Lightloom`.

| File | Purpose |
|---|---|
| `prepare.sh` | writes the files of the Flathub repository for one tag into `dist/flathub/` |
| `flathub.json` | Flathub build options: x86_64 only (the only architecture CI builds and tests) |

The manifest itself is not kept here: `prepare.sh` derives it from
`packaging/flatpak/io.github.MrMoraleDev.Lightloom.yml`, replacing the working-tree `dir`
source (between the `flathub-source` markers) with a `git` source pinned to the tag and its
commit. One manifest, so the weekly `flatpak.yml` build tests what Flathub builds.

## App id

Flathub needs an id under a domain the developer controls. `io.github.MrMoraleDev.Lightloom`
is the GitHub Pages domain of the `MrMoraleDev` account and the `Lightloom` repository:
Flathub verifies it by the GitHub login of the account that owns the repository (the
"verified" badge comes from logging in to flathub.org with that account). The id is used for
the metainfo, the desktop entry, the icon, the tray's D-Bus name
(`io.github.MrMoraleDev.Lightloom.Tray`) and the data directory
(`~/.var/app/io.github.MrMoraleDev.Lightloom`).

## What Flathub builds

Flathub builds offline, from source, on its own builders: no network during the build. The
crates and npm packages come from `cargo-sources.json` and `node-sources.json`, generated by
`packaging/flatpak/generate-sources.sh` (pinned flatpak-builder-tools) from the `Cargo.lock`
and `ui/package-lock.json` **of the pinned commit**; `prepare.sh` reads those lock files with
`git show <commit>:...`, never from the working tree. Regenerate both for every new version.

## No CEF effect renderer yet

The Flatpak builds the daemon, the CLI and the dashboard, not `lightloom-renderer`:
cef-dll-sys downloads the CEF distribution in its build script, which an offline build
cannot do, and Chromium inside the sandbox needs zypak (`packaging/flatpak/README.md`,
"Renderer"). So the effects written as web pages (the HTML/canvas effects in `effects/`) do
not play in the Flatpak; the native effects, per-LED colours, profiles, audio and screen
input do. The metainfo does not promise HTML effects.

**This does not block the submission.** Flathub asks that an app works and that its
description is honest, not that it matches other builds of the same program; the release
tarball, AppImage, .deb and .rpm carry the renderer. Reviewers may ask about it: point them
here.

Things reviewers will ask about, with the answers:

- `--device=all`: hidraw, usbfs, serial and `/dev/i2c-*` nodes. There is no narrower
  permission covering hidraw and i2c (OpenRGB on Flathub, `org.openrgb.OpenRGB`, uses the
  same).
- `--share=network`: the dashboard is served on 127.0.0.1 and opened in the browser outside
  the sandbox; network-device plugins (LAN); udev's netlink hotplug broadcasts.
- Host setup: device access needs udev rules on the host, which a Flatpak cannot install.
  `flatpak run io.github.MrMoraleDev.Lightloom --setup-help` prints the commands, and the
  metainfo description says so. OpenRGB's Flatpak has the same requirement.
- `--system-talk-name=org.freedesktop.login1` (sleep/lock and its delay inhibitor),
  `--talk-name=org.freedesktop.Notifications`, `--talk-name=org.kde.StatusNotifierWatcher`
  (tray icon), `--socket=pulseaudio` (audio-reactive effects).

## Submission steps (first version)

Prerequisites: a published GitHub release whose tag contains this directory and the renamed
`packaging/flatpak/io.github.MrMoraleDev.Lightloom.*` files. **`v0.1.0` predates them** (it
still has `org.lightloom.Lightloom`), so the first submission needs the next tag (for example
`v0.1.1`), with its `<release>` entry added to the metainfo before tagging. Also needed:
Linux with git, python3 (venv) and flatpak-builder, and the GitHub account `MrMoraleDev` (or
one with access to the repository).

1. Generate the files:

   ```sh
   packaging/flathub/prepare.sh --tag v0.1.1      # writes dist/flathub/
   ```

   `dist/flathub/` then holds `io.github.MrMoraleDev.Lightloom.yml` (git source:
   `tag: v0.1.1` and its full `commit:`), `cargo-sources.json`, `node-sources.json` and
   `flathub.json`.

2. Build and lint it locally, as Flathub will:

   ```sh
   flatpak remote-add --user --if-not-exists flathub https://dl.flathub.org/repo/flathub.flatpakrepo
   flatpak install --user -y flathub org.flatpak.Builder
   cd dist/flathub
   flatpak run --command=flathub-build org.flatpak.Builder --install io.github.MrMoraleDev.Lightloom.yml
   flatpak run --command=flatpak-builder-lint org.flatpak.Builder manifest io.github.MrMoraleDev.Lightloom.yml
   flatpak run --command=flatpak-builder-lint org.flatpak.Builder repo repo
   flatpak run io.github.MrMoraleDev.Lightloom --setup-help
   ```

   Every linter error must be fixed (in this repository, then tag again) or have a Flathub
   exception; warnings are fine. `flatpak.yml` runs the same linter weekly on `main`
   (appstream, manifest, builddir, repo).

3. Fork <https://github.com/flathub/flathub> on GitHub. **Untick "Copy the master branch
   only"**: submissions go to the `new-pr` branch.

4. Clone the fork's `new-pr` branch, add the files on a new branch, push:

   ```sh
   git clone --branch=new-pr git@github.com:MrMoraleDev/flathub.git
   cd flathub
   git checkout -b io.github.MrMoraleDev.Lightloom new-pr
   cp ../Lightloom/dist/flathub/* .
   git add io.github.MrMoraleDev.Lightloom.yml cargo-sources.json node-sources.json flathub.json
   git commit -m "Add io.github.MrMoraleDev.Lightloom"
   git push -u origin io.github.MrMoraleDev.Lightloom
   ```

5. Open a pull request against **`flathub/flathub`, base branch `new-pr`** (not `master`),
   titled `Add io.github.MrMoraleDev.Lightloom`. Fill in the template's checklist; paste the
   permission answers above. Comment `bot, build` to start a test build.

6. Reviewers comment on the pull request; changes go into this repository (manifest,
   metainfo), then `prepare.sh` again with a new tag, and a push to the same branch. Once
   approved and merged, Flathub creates `flathub/io.github.MrMoraleDev.Lightloom` and invites
   the submitter; the app appears on flathub.org after the first build there.

7. Log in to flathub.org with the `MrMoraleDev` GitHub account and verify the app (developer
   portal), which the `io.github.MrMoraleDev` id makes possible.

## Later versions

In `flathub/io.github.MrMoraleDev.Lightloom` (not `flathub/flathub`): run
`packaging/flathub/prepare.sh --tag vX.Y.Z`, copy the four files over, open a pull request
against that repository's `master`; Flathub's bot builds it and the merge publishes it.
Add the version's `<release>` to the metainfo before tagging, or the linter and the store
show the old version.
