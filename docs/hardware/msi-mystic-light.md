# MSI Mystic Light motherboards (185-, 162- and 112-byte controllers)

Plugins: `plugins/msi-mystic-light` (vendor id 0x1462) and `plugins/msi-mystic-light-common`
(vendor id 0x0DB0, product id 0x0076). They share `protocol.js` and `boards.js` byte for byte (a
plugin has a single `VendorId()`, hence two directories; the tests check the copies are identical).
Status: **untested on hardware** (`tested` is empty in both manifests). The MAG B550 TOMAHAWK
(1462:7C91) is deliberately left to `plugins/msi-mystic-light-7c91`, which was validated on that
board (see [msi-mystic-light-185.md](msi-mystic-light-185.md)).

run on a file whose header is not GPL-2.0-or-later). The script and the fixture generator ran from a
scratch directory and are not part of the repository.

## Device ids and collections

`REGISTER_HID_DETECTOR_PU(name, DetectMSIMotherboardControllers, vid, pid, page, usage)`:

* vendor 0x1462: 109 product ids compiled by default (usage page 0x0001, usage 0x00). The plugin
  claims 108 of them: all but 0x7C91. `Validate()` accepts only the 0x0001/0x00 collection.
* vendor 0x0DB0, product 0x0076 (`MSI_USB_PID_COMMON`): "MSI Mystic Light Common" on 0x0001/0x00
  and "MSI Mystic Light X870" on 0xFF00/0x01; `Validate()` accepts both. OpenRGB runs its detector on
  each collection, while Lightloom activates the first validated one, so `Initialize()` uses
  `getHidEndpoints()` / `set_endpoint()` to try 0x0001/0x00 first and moves to 0xFF00/0x01 only when
  the first answered the detection read with an unsupported length (nothing is written before that).
  Without those host calls the active collection is used as is.
* left out, as in OpenRGB: the 13 product ids under `#ifdef ENABLE_UNTESTED_MYSTIC_LIGHT` (3EA4,
  4459, 7B10, 7B94, 7B96, 7C42, 7C70, 7C85, 7C88, 7C89, 7C96, 7C99, 905D), which OpenRGB does not
  compile ("bricking risk"). The `REGISTER_CUSTOM_UDEV_RULE` lines (7E12, 7E16, 7E24, 7E26, 7E27,
  7E49) are Linux permission rules, not detectors; those boards are reached through 0DB0:0076.

## Detection and start-up (`Initialize()`)

1. `GET_FEATURE 0x52` with a 200-byte buffer (`device.get_report([0x52], 200)`); the length the
   device returned (`getLastReadSize()`) picks the variant: 185 or 186 bytes = 185-byte controller,
   162/163 = 162, 112/113 = 112. Anything else: log and stop (no write of any kind).
2. Firmware queries (`ReadFwVersion()`): output report `01 B0` + 62 x `CC` (64 bytes), read one
   input report; then `01 B6` + 62 x `CC`, read one input report. Byte 2 of the first reply is the
   APROM version. OpenRGB's `hid_read` blocks; Lightloom reads with a 1 s timeout. Unlike OpenRGB,
   Lightloom empties the input queue (`clearReadBuffer()`) before each query and accepts a reply only
   if it starts `01 B0` (resp. `01 B6`); no reply or a foreign one = version 0, which refuses a board
   with a minimum firmware (the version is a safety gate here).
3. 185-byte only: the board id is the USB product id, or for product id 0x0076 the first four
   characters of the USB serial number read as hex (`std::stoi(.., 16)`; `parseInt` also reads the
   leading hex digits). The first `board_configs[]` row with that id is used; without a row: 6 onboard
   LEDs, 1 + 1 pipe LEDs, 2 JRGB, every zone, **no Direct mode**. If the row's minimum firmware is not
   met (MPG B550 GAMING PLUS 7C56 needs APROM >= 6) start-up stops before the next read, as in OpenRGB.
   Board ids >= 0x7D03 use "mixed mode" record placement (below).
4. `GET_FEATURE 0x52` of exactly the variant's length (`ReadSettings()`). This is the **restore
   image**. Unless the full report comes back (length to length + 1 bytes, report id 0x52 first),
   nothing is ever written in this session. 162-byte boards look their row up here (no row: 10
   onboard LEDs, `zones_set0`); 112-byte boards have no table (JRGB1, JRAINBOW1, JCORSAIR, 7 onboard
   LEDs).
5. Boards whose 185-byte row says `DIRECT_MODE_DISABLED` (and 185-byte boards without a row) have no
   Direct mode in OpenRGB; start-up stops here and nothing is written.
6. OpenRGB's "Direct" mode is selected (below).

## Report 0x52 (configuration)

One 10-byte record per zone: `+0` effect, `+1..+3` colour 1 (R, G, B), `+4` speed (bits 0-1) /
brightness (bits 2-6) / "sync JRGB" (bit 7), `+5..+7` colour 2, `+8` sync flags (bits 0-5) / custom
colour (bit 7), `+9` padding. JRAINBOW records add `+10` LED count; the 185-byte JCORSAIR record is
`effect, R, G, B, fan_flags, quantity, padding[4], is_individual` (its `+10` doubles as the JRAINBOW3
LED count). The **last byte is the save-to-flash flag; every 0x52 report Lightloom sends has it 0, except the
"Save to devices" reports (see below).**

| Variant | Records (offset) |
|---|---|
| 185 | JRGB1 0x01, JPIPE1 0x0B, JPIPE2 0x15, JRAINBOW1 0x1F (11 bytes), JRAINBOW2 0x2A (11), JCORSAIR 0x35 (11), JCORSAIR outer 0x40, onboard 0x4A, onboard 1-9 0x54..0xA4, JRGB2 0xAE, save 0xB8 |
| 162 | JRGB1 1, JRAINBOW1 11, JCORSAIR 21, JCORSAIR outer 31, onboard 41, onboard 1-10 51..141 (JRAINBOW2 is onboard 10, 141), JRGB2 151, save 161 |
| 112 | JRGB1 1, JRAINBOW1 11, JCORSAIR 21, JCORSAIR outer 31, onboard 41, onboard 1-6 51..101, save 111 |

Mixed mode (185-byte, board id >= 0x7D03): JRGB2 is the `on_board_led_6` record (0x86) and onboard
LED 6 the `j_corsair_outerll120` record (0x40).

## Direct mode, per variant

**185-byte, `DIRECT_MODE_PER_LED`** (85 table rows). Switch: one 0x52 report built from scratch
(`enable_per_led_msg`): JRGB1 `+4 08 +8 80`; JPIPE1/2 `+4 2A +8 80`; JRAINBOW1/2 `+4 29 +8 80`;
JCORSAIR `+4 29 +5 00 +8 82 +10 78`; JCORSAIR outer `+4 28 +8 80`; onboard `+0 25 +4 A9 +8 BF`;
onboard 1-9 `+4 28 +8 80`; JRGB2 `+4 2A +8 80`; every effect byte not named is 01 (static), colours
are 0. Then per frame 725-byte feature reports 0x53: `53 25 <hdr1> <hdr2> 00` and 240 LEDs of R, G, B.

* Synchronised (JRAINBOW1 <= 40, JRAINBOW2 <= 40 and JRAINBOW3 <= 120 LEDs): the switch has
  JRAINBOW1/2 `+0 01 +10 28`, JCORSAIR `+0 01 +10 78`, onboard `+8 BF`; one stream per frame, header
  `53 25 06 00 00`, slots: onboard LEDs, PIPE1 LEDs, PIPE2 LEDs, the JRGB slots (JRGB1, JRGB2), 40
  JRAINBOW1 slots, 40 JRAINBOW2 slots, 120 JCORSAIR/JRAINBOW3 slots (counts from the board row).
* Not synchronised: the switch sets each present header's record to `+0 25` with `+10` C8
  (JRAINBOW1), F0 (JRAINBOW2) or F0 (JCORSAIR/JRAINBOW3), onboard `+8 B1`; per frame one stream per
  present header (`53 25 04 00 00` JRAINBOW1, `53 25 04 01 00` JRAINBOW2, `53 25 05 00 00`
  JCORSAIR/JRAINBOW3), each followed by a 13 ms pause, then the onboard stream `53 25 06 00 00`.
* The decision reads the LED counts at JRAINBOW1/2 `+10` and JCORSAIR `+10` of the board's 0x52
  image, overwritten by the sizes of the JRAINBOW zones the board has (so an absent JRAINBOW2 or a
  JCORSAIR board's `+10` byte still counts, as in OpenRGB). Changing a JRAINBOW size while Direct is
  on re-sends the switch once per JRAINBOW zone (OpenRGB's `SetupZones()` calling `SetZoneLEDCount()`).
* Stream buffers keep their previous contents; only the LEDs of the current zones are overwritten
  (zone order of the board's zone set, each zone's LEDs last to first, later zones win on a shared
  slot, e.g. JRGB1 and JRAINBOW1 LED 1 on PRO H610M-G DDR4 7D46, whose row has 0 JRGB slots).
* A board whose zones are only JRGB/PIPE (MPG Z790-S WIFI 7D88: JRGB1 only): OpenRGB sends the
  switch but never a stream (`Update()` returns early when no onboard/JRAINBOW/JCORSAIR zone
  exists), so the LEDs stay dark for the whole session. **Deviation:** Lightloom writes nothing at all
  on such a board (logs it), so the board keeps its own effect. The fixture `185-7d88-no-stream`
  still records OpenRGB's switch; the test expects the same reads and no write.

**185-byte, `DIRECT_MODE_ZONE_BASED`** (7 rows): per frame one 0x52 report built from scratch
(`zone_based_per_led_data`: every record effect 01; JRGB1/2, JPIPE1/2, JRAINBOW1/2, onboard 0-9
`+4 28 +8 80`; JRAINBOW `+10` 64; JCORSAIR `+4 28`), with colour 1 = colour 2 = the LED colour: JRGB1,
JRGB2, JRAINBOW1/2 and PIPE1/2 (first LED only), JCORSAIR/JRAINBOW3 (JCORSAIR record: colour 2 lands
in `quantity, padding[0..1]`), onboard LED n in the `on_board_led_{n+1}` record (the master record
keeps no colour).

**162-byte** (OpenRGB's "Direct" is the static effect): per frame the board's own 0x52 image (as
read, with the onboard master `+8` first set to 81) where, for each LED: effect 01, `+4 28`,
`+8 |= 80`, `+9 00` (zones up to the onboard master also clear `+4` bit 7 and `+8` bit 0), colour 1 =
colour 2. Onboard LED n writes record `on_board_led_{n+1}` (LED 1 also the master). Right after the
switch OpenRGB sends one report with the colours read from the board (`GetDeviceConfig()`); the
plugin does the same in `Initialize()`.

`+4 28` / `+8 |= 80` are the Direct mode **at its own defaults** (brightness 10, per-LED colours),
which is what the fixtures drive. **Deviation:** OpenRGB's `GetDeviceConfig()` also runs in the
RGBController constructor and, when the first zone of the board's zone set reads as Static (effect
01, the value of OpenRGB's "Direct" entry), copies that zone's brightness into the Direct mode, and
sets the mode to random colours whenever that zone's custom-colour bit 0x80 is **set** (its
`GetMode()` returns the custom-colour bit as the "rainbow" flag, i.e. inverted). `UpdateLed()` then
calls `SetMode(.., random = true)`, which clears `+8` bit 7 in every record it writes, so the board
ignores the colours sent. Lightloom always sends brightness 10 (Lightloom applies brightness to the
colours itself) and keeps the custom-colour bit set. The fixture
`162-7b85-static-first-openrgb-config` records OpenRGB's bytes for such an image (here `+4` 10
instead of 28, `+8` without bit 7); the test checks the plugin differs from it only in those two
fields, and `162-7b85-static-first` (same image, Direct at its defaults) byte for byte.

**112-byte**: per frame one 0x52 report built from scratch (every record effect 01; JRGB1,
JRAINBOW1, onboard 0-6 `+4 28 +8 80`): JRGB1, JRAINBOW1, JCORSAIR and onboard LED n in
`on_board_led_{n+1}` (onboard LED 7 has no record and is dropped, as in OpenRGB).

A frame whose reports are identical to the previous frame's is resent only once a second. Frames
are not otherwise rate-limited: on 162/112-byte and zone-based 185-byte boards every changed frame
(up to the host's ~30 per second) is one SET_FEATURE 0x52 with the save byte 0, which is also what
OpenRGB's Direct mode sends per update on these boards, and what the hardware-validated 7C91 plugin
sent at 30 fps in its first milestone (see msi-mystic-light-185.md, "Performance") without a fault.
OpenRGB's "bricking risk" warning concerns the `ENABLE_UNTESTED_MYSTIC_LIGHT` product ids, which are
not claimed.

## Geometry

Zones keep OpenRGB's names and order. Fixed zones (JRGB1/2, PIPE1/2, ONBOARD, and every zone on
162/112-byte boards) are rows of the device's LED grid, one row per zone, LEDs at x = index. On
per-LED 185-byte boards the resizable ARGB zones are channels (`JRAINBOW1` up to 200 LEDs,
`JRAINBOW2`, `JRAINBOW3`, `JCORSAIR` up to 240) whose LED count comes from the channel's components;
they play the part of OpenRGB's profile sizes (zones start at 0 and are resized, in zone order, when
they have LEDs). On zone-based boards the ARGB zones are "effects only" in OpenRGB and take one
colour: they are one-LED rows here (OpenRGB lets them be sized 0-30 but only uses LED 1; with a size
above 1 its update loop reads other zones' colours, which is not reproduced).

## Shutdown

OpenRGB has no exit step, and in Direct mode its `Update()` never writes a read image back (only
its non-direct hardware-effect branch re-reads and resends the configuration). The restore is a
Lightloom addition: it writes the image read at start-up back (`Shutdown(false)` and `Shutdown(true)`
alike, save byte 0), which leaves Direct mode and returns the board to its own effect. Nothing is
sent if the session never wrote.

* 185-byte images: on the 7C91 the J_CORSAIR record `+9` (0x3E) reads back as the written value + 4
  ([msi-mystic-light-185.md](msi-mystic-light-185.md)), so a verbatim write-back would raise it by 4
  per session (on 3-header boards that record is JRAINBOW3). The restore therefore writes `read - 4`
  there (values below 4 as read), as `plugins/msi-mystic-light-7c91` does. On a board without the
  bias the byte would instead sink by 4 per session until it is below 4; OpenRGB's own reports write
  0 there. Not verified on any board other than the 7C91.
* If the board was already in per-LED mode when read (onboard master effect `0x25`: left by another
  program, or by a Lightloom session that ended without `Shutdown`), the restore image keeps that mode
  and the board shows the last streamed colours after exit; the plugin logs it at start-up. There is
  no stored hardware effect to fall back to that would not be invented.

## Save to devices and exit modes (Lightloom extensions, untested on hardware)

"Save to devices" ([docs/host-api/save-shutdown.md](../host-api/save-shutdown.md)) is OpenRGB's
`DeviceSaveMode()` for its Static or Breathing mode: `protocol.js` `save()` builds the 0x52 report
on the restore image with `SetMode()` + `SetZoneColor()` for every zone of the board (one colour
per zone, the average of its LEDs; colour 2 = colour 1; brightness 100 %; speed medium for
breathing; custom-colour flag; on 185-byte boards the onboard zone copied to the `numof_onboard_leds`
onboard records and its JRGB / pipe sync cleared, as `SetMode()` does for modes up to Lightning,
JRAINBOW LED counts from the channels), then sends it as OpenRGB's `Update(true)` does:

* 185 bytes (`MSIMotherboard185Controller::Update(true)`): GET 0x52, SET it back with the save byte
  set, SET the new report with the save byte set; then GET 0x52 again (the new restore image) and
  back to Direct (the enable-per-LED report on per-LED boards).
* 162 bytes (`MSIMotherboard162Controller::Update(true)`): one SET with the save byte set.
* 112 bytes: not offered (refused at preview).

Exit modes: `"keep"` / `"off"` send the same Static report with the last colours or black and the
save byte 0 (112-byte boards: a Direct frame). Tests: `tests/plugin.test.mjs` ("save", "exit
modes", "the save byte is set only by SaveToDevice").

## Not ported

* The hardware effects other than Static and Breathing (Flashing ... Fire), and the automatic-save
  flag. Static and Breathing exist only as "Save to devices" choices (above).
* OpenRGB's non-direct `Update()` outside the save.
* The 761-byte controller (see Sources).
* The DMI board name (OpenRGB names the device "MSI " + DMI mainboard; Lightloom uses the table name).
* Nothing in these reports touches fans, pumps or other non-lighting settings (the JCORSAIR
  `fan_flags` byte is a lighting field of the Corsair-header record; it is sent as OpenRGB sends it).

## Fixtures and tests

`fixtures/openrgb-direct.json` (0x1462) and `fixtures/openrgb-common.json` (0x0DB0) were produced
by **OpenRGB's own code**, not by the plugin: the 185/162/112 controller and RGBController sources
above were compiled unchanged (MinGW g++ 6.3) against a scratch fake hidapi and minimal
`RGBController` / `LogManager` / `StringUtils` stand-ins, driven like OpenRGB's detector, profile
manager and Direct mode, with test colours that encode zone, LED index and frame. Each scenario
records every hidapi call. The tests replay each scenario through `plugin.js` on
`plugins/_testkit/mock-device.mjs` and require the same sequence of `GET_FEATURE`, output writes,
input reads, `SET_FEATURE` bytes and pauses, then check the restore on shutdown, the save byte, the
geometry, the refusal to write without a read, and the identity of the shared files. Scenarios:
7C79 (sync, non-sync, resize while active, image already in per-LED mode), 7D86 (JRAINBOW3
sync/non-sync), 7C60 (JCORSAIR; image byte forcing non-sync), 7C67 (image JRAINBOW2 count on a board
without that zone), 7D46 (shared slot), 7C77, 7D03 (15 + 18 pipe LEDs), 7D69 (9 onboard, three
headers non-sync), 7C56 (firmware 5 refused, 6 accepted), zone-based 7C37 / 7E28 (mixed mode) / 7C34,
7C59 and 7B16 (no Direct mode), 7D88 (switch only in OpenRGB; no write in Lightloom), 162-byte 7B85 /
7B85 with a Static first zone (Direct at its defaults, and as `GetDeviceConfig()` leaves it) / 7B50 /
B926 / 7D04 (no row) / 1720 (10 onboard), 112-byte, and 0DB0:0076 with serials 7E12, 7E28, 0076 and
an unknown one. The common plugin's tests also cover the collection order on 0DB0:0076.

Vendor software: `ConflictingProcesses()` lists MSI's lighting services (`LEDKeeper.exe`,
`LEDKeeper2.exe`, `LightKeeperService.exe`, `LightKeeperService2.exe`), the list of the
hardware-validated `msi-mystic-light-7c91` plugin.

Cross-check with the 7C91 recording (`plugins/msi-mystic-light-7c91/fixtures/per-led.json`): the
recorded switch report has the same records as OpenRGB's synchronised switch except the JRAINBOW
`+10` LED counts (the recording carries the strips' real counts, OpenRGB always 0x28) and the
JCORSAIR `+10` byte (01 recorded, 0x78 in OpenRGB); the stream header `53 25 06 00 00` and the
onboard / JRGB slot order match, but the recording packs JRAINBOW2 right after JRAINBOW1 where
OpenRGB reserves 40 slots for each. The recording also starts with an all-zero 0x53 report that
OpenRGB does not send.

## Untested / open

* No board of this family other than the 7C91 (not covered here) has been run with these plugins.
* Whether boards answer the firmware queries within the 1 s timeout (OpenRGB waits forever).
* Whether the JCORSAIR `+9` read-back bias of the 7C91 holds on the other 185-byte boards (the
  restore assumes it does; see Shutdown).
* The 0xFF00/0x01 collection of 0DB0:0076 ("X870") is claimed as OpenRGB does; which report sizes it
  answers with is unknown (761-byte boards are left alone).
